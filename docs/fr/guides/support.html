Guide · Assistance

Quelque chose ne marche pas ? Dites à l’auteur ce que vous avez vu.

FileDO est conçu et suivi par une seule personne. Avec un signalement qui indique la version, ce que vous avez fait et ce qui s’est passé, l’auteur peut travailler. Ci-dessous : où l’envoyer, ce qu’il doit contenir et ce qu’il faut lire d’abord.

1. Où signaler un problème

Deux moyens de joindre l’auteur, tous deux gratuits, plus un raccourci depuis le programme. Choisissez selon ce que vous voulez partager.

GitHub issues

L’endroit pour les bugs, les questions et les idées. Il faut un compte GitHub gratuit, et une issue est publique : tout le monde peut la lire.

Ouvrir le suivi des issues

E-mail

Pour tout ce que vous préférez ne pas publier, ou si vous n’utilisez pas GitHub. Écrivez à sza@ukr.net en indiquant FileDO et la version dans l’objet.

Depuis le programme

La page À propos de la fenêtre FileDO contient le lien Signaler un problème, l’adresse de l’auteur et le bouton Envoyer les logs à l’auteur (section 3).

2. Ce qu’il faut indiquer

Cinq informations font d’un signalement quelque chose que l’auteur peut reproduire lui-même.

  1. La version de FileDO. Dans la fenêtre FileDO, ouvrez la page À propos et lisez la ligne « Version de l’interface : ». Dans un terminal, lancez filedo --no-ui : le haut de la sortie affiche la date, l’adresse de l’auteur et la version, un nombre à dix chiffres. Donnez ce nombre plutôt que celui de la liste des applications installées de Windows, qui peut être écrit autrement.
  2. Comment vous l’avez installé, et votre Windows. Setup EXE, MSI, ZIP, winget ou Microsoft Store : les versions diffèrent par ce qu’elles savent faire. Dites laquelle vous avez, ainsi que votre version de Windows (winver l’affiche).
  3. Ce que vous avez fait, précisément. La commande telle que vous l’avez saisie (la page Commande de la fenêtre l’affiche et peut la copier), ou la page et les boutons utilisés. N’indiquez aucun mot de passe.
  4. Ce qui s’est passé, et ce que vous attendiez. Reproduisez les messages mot pour mot. Ajoutez le code de sortie : une fois la commande terminée, echo %ERRORLEVEL% dans l’invite de commandes ou $LASTEXITCODE dans PowerShell l’affiche. 0 veut dire réussi ou terminé, 1 défaut trouvé, 2 vérification impossible. Les commandes de conteneur (secure, unsecure, reveal, vd) utilisent un jeu de codes plus large, listé dans le README.
  5. Des logs, si possible. La section 3 montre comment en obtenir sans chercher de fichiers.

3. Les logs, si vous pouvez les envoyer

La page À propos a un bouton Envoyer les logs à l’auteur. Il regroupe dans un ZIP les logs texte que FileDO a écrits sur cet ordinateur, ouvre le dossier avec le ZIP sélectionné, place son chemin dans le presse-papiers et ouvre votre messagerie avec l’adresse de l’auteur déjà saisie. Vous voyez d’abord le ZIP, et rien n’est envoyé tant que vous n’avez pas vous-même cliqué sur Envoyer.

Un lien de messagerie ne peut pas porter de pièce jointe : c’est donc à vous de joindre le ZIP, dont le chemin est déjà dans le presse-papiers.

Lisez le ZIP avant de le joindre. Dans les lignes regroupées, les identifiants, les liens et les chemins absolus sont remplacés par [REDACTED], mais un texte libre peut encore contenir des informations personnelles. Une issue GitHub est publique : ne joignez le ZIP qu’après l’avoir lu, ou envoyez-le plutôt par e-mail.

L’historique, les listes de contrôle et les rapports JSON ne sont pas dans le ZIP, car ils peuvent contenir les noms de vos propres fichiers et dossiers. La page de confidentialité liste les fichiers que FileDO écrit, où ils se trouvent et ce qu’ils contiennent. Ne mettez jamais de mot de passe de conteneur dans un signalement.

5. À quoi s’attendre

FileDO n’a qu’un seul mainteneur et aucune équipe d’assistance. Aucun délai de réponse n’est promis : un signalement est lu quand l’auteur le peut, et un correctif, s’il y en a un, paraît avec une version ultérieure - les notes de version montrent ce qui a changé. Un signalement qui suit la section 2 est plus facile à traiter.
